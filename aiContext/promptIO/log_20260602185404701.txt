### What These Rules Mean in Practice

Rule 1-3 (Reuse First):
  Before writing any new class or method, I must check whether Actions, AssertUtils, Reporter, ConfigReader, Util, TestDataManager, ContextManager, ScenarioManager, WebDriverFactory, existing Pages, Components, or wrapper classes already cover the need. New code is the last resort, not the first.

Rule 4 (Consistency):
  All new code must follow the existing package layout (assertions / driverConfig / enums / hooks / utilities in main; runners / web/components / web/pages / web/steps / web/dataManager in test), use the same naming patterns (e.g., NavBar, LogInPanel, HomePageSteps), and match the coding style already present (@author tag, final utilities, private constructors, etc.).

Rule 5 (Extend over create):
  If a component like NavBar or LogInPanel almost covers a need, prefer adding a method to it rather than creating a parallel component.

Rule 6-7 (Quality standards):
  No quick hacks. All generated code must be production-ready, follow SOLID principles (single responsibility, open/closed, etc.), and match patterns already seen in the framework (e.g., ThreadLocal for parallel safety, AtomicInteger for counters, ConcurrentHashMap for caches).

Rule 8 (Logging + exceptions):
  Use Reporter.log() for step-level logging. Use Actions.stopTestException() for wrapping Selenium errors. Provide meaningful messages. Never swallow exceptions silently.

Rule 9 (No hardcoding):
  Use Timeouts enum for wait durations, config.properties / RuntimeConfig for environment values, testData JSON + TestDataManager for test data. No magic strings or numbers.

Rule 10 (Pre-generation analysis required):
  Before producing any code artifact, I must explicitly state:
    - Which existing components I reviewed
    - Which I am reusing (and how)
    - Why a new component is needed (if any)
  This ensures the response is deliberate and traceable.
